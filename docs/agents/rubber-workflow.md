# rubber-workflow

한 덩어리의 작업을 DELTA 단위로 나눠 실행하는 절차. "로드맵"이라는 단어가 무엇을 할지 정리한
문서(`ROADMAP.md`)와 어떻게 실행할지 정하는 절차 양쪽에서 다른 뜻으로 쓰이면 혼란스러워서, 이
저장소에서는 실행 절차를 "rubber-workflow"라고 부른다. 구현 전에 모든 DELTA의 계획을 먼저
작성하고, 작업 중 발견에 따라 DELTA를 수정·추가·분할하는 탄력성("고무")이 핵심이다.

## 진입 경로

다음 둘 중 하나로 시작한다.

- **브레인스토밍**: 사용자와 논의해 확정한 작업(브레인스토밍 스킬의 설계 승인 등). 관련
  ROADMAP 항목이 없다.
- **ROADMAP.md 항목**: 루트 `ROADMAP.md`의 항목 하나를 실행.

둘 다 아래 절차는 동일하다. ROADMAP.md 항목에서 시작했으면 "마무리"에서 `ROADMAP.md`도
갱신한다.

## 언제 쓰나

한 번에 끝내기엔 크다고 판단되는 작업. 사소한 작업(문서 한 파일 수정, 설정 한 줄 변경)에는
쓰지 않는다 — 그런 작업은 바로 한다.

## 작업공간

`_works/<yyyyMMdd>-NN-<제목>/` (`_works/`는 `.gitignore` 대상). `_works/` 바로 아래에서
`yyyyMMdd-NN-` 접두어가 붙은 폴더만 작업 폴더로 취급하고, 다른 항목은 작업과 무관한 자료이므로
건드리지 않는다. 완료된 작업 폴더는 `_works/_completed/`로 옮긴다(아래 "마무리" 참고) — 진행
중인 작업 폴더만 `_works/` 바로 아래에 있다.

```text
_works/20260921-01-example-task/
  _meta.md               # 작업 브랜치·관련 ROADMAP 항목·상태 — 다른 에이전트가 이어받기 위한 최소 정보
  checklist.md            # 목표·범위·DELTA 목록·최종 완료 조건
  DELTA-01.md
  DELTA-02.md
  DELTA-02a.md            # 작업 중 분할/추가된 것
  pending-traps/
    01.md ...
  pending-issues/
    01.md ...
```

## 시작

작업 폴더를 만들고 `_meta.md`, `checklist.md`, 모든 `DELTA-NN.md`를 순서대로 작성한 뒤
브랜치를 만든다. **모든 DELTA의 "## 계획"을 채우기 전에는 구현을 시작하지 않는다.**

```markdown
---
작업 브랜치: example-task
관련 ROADMAP 항목: 없음 # ROADMAP.md 항목에서 시작했으면 해당 항목
상태: 진행중
---
```

`_meta.md`는 이 세 필드만 가진다. **진행 로그를 쓰지 않는다** — 판단이 필요했던 지점은
해당 `DELTA-NN.md`의 "## 결정" 절에 남긴다(아래 "DELTA-NN.md 형식" 참고). 상태는 `진행중`
/ `완료` 둘 뿐이고, 다른 에이전트가 이 작업 폴더를 이어받아도 되는지 판정하는 용도로만
쓴다.

계획 문서 작성 후 `git switch -c <작업 브랜치> dev`로 브랜치를 만든다. 기준 브랜치는 `dev`다 — `main`에서 분기하거나 `main`에 병합하지 않는다. 브랜치 상태가 바뀌면 실제 저장소 상태를 먼저 확인한다.

## checklist.md

작업 시작 시 작성. DELTA 목록은 작업 전체 범위를 덮도록 전부 적는다.

```markdown
# <제목> 완료 체크리스트

- 목표: ...
- 범위(포함/제외): ...
- 관련 ROADMAP 항목: ROADMAP.md#<항목> (브레인스토밍에서 시작했으면 생략)

## DELTA 목록

- [ ] DELTA-01: <한 줄 스코프>
- [ ] DELTA-02: <한 줄 스코프>

## 완료 조건

- [ ] 조건 1
- [ ] 조건 2
```

DELTA 목록의 각 항목은 시작 시점에 `DELTA-NN.md`를 만들고 "## 계획"을 채운다. 목록과
계획을 모두 작성한 뒤 구현에 들어간다.

DELTA 목록과 계획은 **확정이 아니다** — 작업 중 필요하면 수정·추가·분할한다(별도 승인
없이). 빠진 게 발견되면 목록에 한 줄 추가하고 해당 `DELTA-NN.md`의 "## 계획"을 작성한 뒤
계속 진행한다. 기존 DELTA를 쪼개야 하면 `DELTA-01a`, `DELTA-01b` 형태로 추가한다(뒤 번호를
밀지 않음). 아직 시작하지 않은 DELTA의 계획이 발견과 맞지 않으면 그 계획을 고친다. 완료한
DELTA의 "## 계획"은 고치지 않는다 — 추가 변경은 새 DELTA로 만든다.

완료 조건은 **필수 통과 / 허용 편차 / 제외**를 구분해 적는다. 이전 구현이나 다른 기능의
하니스·시나리오 정의를 옮겨 오면 기존에 등록된 편차와 예외를 대조해, 편차에 해당하는 항목은
처음부터 "허용 편차"에 둔다. 등록 편차가 있는데 "전부 통과"를 요구하는 완료 조건을 만들지
않는다.

## DELTA-NN.md 형식

```markdown
# DELTA-NN <한 줄 제목>

## 계획

- 목적:
- 변경 대상:
- 완료 기준(검증 방법 포함):

## 결과

<!-- 비어 있으면 이 DELTA는 아직 진행 중(또는 미시작)이라는 뜻. 시작 시점에는 비워 둔다 -->

- 상태:
- 검증 근거:
- 발견/처리:
- 남은 위험:

## 결정

<!-- 판단이 필요했던 지점만, 있을 때만 추가. append-only -->
```

"## 결정"은 이 DELTA를 진행하며 애매한 것을 임의로 골라야 했던 지점을 남긴다 — 주제,
결정, 근거, 틀렸을 때 비용을 적는다. 없으면 절 자체를 생략한다.

## DELTA 사이클

모든 DELTA의 계획을 작성한 뒤 시작한다. DELTA 하나 = 계획 재확인 → 구현 → 확인 → 정리,
한 번에 끝까지.

1. checklist의 DELTA 목록에서 다음 하나를 고른다(번호 순서 고정 아님).
2. `DELTA-NN.md`의 "## 계획"을 다시 읽고, 앞 DELTA의 결과와 맞지 않으면 먼저 고친다.
3. 구현한다. 테스트 가능한 부분은 실패(RED) 확인 후 최소 구현으로 통과(GREEN).
4. 완료 기준을 실제로 확인한다(`pnpm check-types`, `pnpm lint`, `pnpm test`, `pnpm build`
   중 범위에 해당하는 명령의 실행 결과, 브라우저 확인 등 — 근거를 남긴다).
5. `DELTA-NN.md`의 "## 결과"에 상태·검증 근거·발견한 것·남은 위험을 적는다.
6. 함정/후속 작업을 발견하면 `pending-traps/`, `pending-issues/`에 바로 적어둔다 — 승격
   판단은 지금 하지 않는다. 단, 발견이 뒤 DELTA의 계획 문구나 checklist의 완료 조건과
   모순되면 그 문구를 지금 고친다(뒤 DELTA에서 재판단하도록 미루지 않는다). 새 DELTA가
   필요하면 checklist 목록과 `DELTA-NN.md` 계획을 지금 추가한다. 완료 조건을
   약하게 만드는 변경은 아래 "작업 분할과 완료 조건 변경"을 따른다.
7. checklist의 DELTA 체크박스와 완료 조건을 갱신한다.
8. 작업 브랜치에 커밋한다(아래 "브랜치와 병합" — 자유롭게, 매번 확인받지 않음).
9. 다음 DELTA를 고른다. 목록이 비면 완료 조건을 재확인하고, 다 채웠으면 마무리한다.

### 작업 분할과 완료 조건 변경

- 기존 범위를 `DELTA-06a`·`06b`처럼 나누는 것은 실행상의 선택이다. 별도 승인 없이 한다.
- 완료 조건을 바꾸는 것(실패한 셀을 편차로 제외, 판정선 완화, 지원 범위 추가)은 별도
  결정이다. 해당 DELTA의 "## 결정"에 주제·바꾼 문구·근거를 적고 **사용자 확인을 받은 뒤**
  checklist를 고친다. 분할한 DELTA 안에서 문서 갱신과 함께 조용히 처리하지 않는다.
- checklist의 "멈추는 지점"이 발동했으면 자체 해결(측정법 변경, 스크립트 수정) 여부와
  무관하게 "## 결정"에 발동 사실·1차 결과·해결 근거를 적는다.
- 완료 보고(checklist 완료 조건, `ROADMAP.md` 완료 기준)는 성공과 예외를 함께 적는다.
  예: 복귀 240/240, 형식 10/12셀, 편차 2셀 수용(근거). 실측으로 원래 요구를 덮어쓰지 않는다.

## 이어받기 (다른 에이전트가 이어서 진행)

새 에이전트는 대화 맥락 없이 작업 폴더 경로만 받을 수 있다. 다음 순서로 상태를 복원한다.

1. `_meta.md`를 읽는다. `상태: 완료`면 더 할 일이 없다 — 사용자에게 보고하고 멈춘다.
2. `git switch <작업 브랜치>`로 전환한다. 브랜치가 없으면 사용자에게 보고하고 멈춘다 —
   추측해서 새로 만들지 않는다.
3. `checklist.md`를 읽어 목표·범위·완료 조건·DELTA 목록(체크 상태)을 파악한다.
4. 존재하는 `DELTA-NN.md`를 번호 순으로 읽는다. "## 결과"가 채워져 있으면 그 DELTA는
   완료된 것이다. **"## 결과"가 비어 있는 DELTA는 진행 중이거나 미시작이다.** 작업 트리와
   브랜치 커밋으로 진행 중인 DELTA를 판별해 그 DELTA부터 계속한다. 진행 중인 DELTA가 없으면
   checklist에서 체크되지 않은 다음 DELTA를 고른다.
5. 각 `DELTA-NN.md`의 "## 결정"(있으면)을 읽어 이미 내린 판단과 근거를 파악한다. 같은
   판단을 다시 하지 않는다.
6. `pending-traps/`, `pending-issues/`에 이미 있는 임시 기록은 그대로 두고 이어서
   추가한다 — 마무리 시점 전까지 승격 여부를 판단하지 않는다.

무엇이 없거나 애매하면(브랜치가 없다, `_meta.md`가 없다, checklist 목록에 있는 DELTA의
파일이나 "## 계획"이 없다, 진행 중인 DELTA가 둘 이상으로 보인다 등) 추측해서 진행하지 않고
사용자에게 보고한다.

## 브랜치와 병합

- 작업 브랜치는 기준 브랜치 `dev`에서 분기하고, 완료 후 `dev`에 병합한다. `main` 갱신은 이 절차 밖이다.
- 브랜치 이름은 작업 폴더의 `<제목>`(날짜 접두어 제외). 예: `example-task`.
- DELTA 진행 중에는 작업 브랜치에 필요한 만큼 자유롭게 커밋한다(매번 확인받지 않음).
- checklist를 다 채우면 `dev`에 병합하기 전에 커밋을 의미 단위로 재그룹화해 커밋 수를 줄인다(아래 "재그룹화").
  병합은 `dev`에 `git merge --ff-only`로 한다.
- push, rebase, force push는 이 절차에 포함되지 않으며 별도 지시 없이는 하지 않는다.
- 작업 브랜치의 커밋 해시는 재그룹화로 바뀔 수 있다 — 기준 브랜치에 병합되기 전까지 checklist·
  DELTA 문서·이슈 초안에 해시를 적지 않는다. 참조는 파일 경로·DELTA 번호·테스트 이름으로
  한다.

### 재그룹화

`git rebase -i`는 쓰지 않는다 — 에이전트 세션은 `GIT_EDITOR`가 비대화형이라 아무것도
합치지 않은 채 "Successfully rebased"를 반환할 수 있다(`GIT_SEQUENCE_EDITOR` 우회도
마찬가지). 대신:

1. 백업 ref를 남긴다: `git update-ref refs/backup/<브랜치>-pre-squash HEAD`
2. `git log --oneline --name-only <기준-브랜치>..HEAD`로 의미 단위 그룹을 정한다.
3. `git switch --detach <기준-브랜치>` 후 그룹별로 `git cherry-pick -n <커밋...>`과
   `git commit -m "..."`을 반복한다.
4. `git diff refs/backup/<브랜치>-pre-squash HEAD --stat`로 트리가 같은지 대조한다(의도적
   으로 버린 커밋이 없다면 빈 출력).
5. `git branch -f <브랜치> HEAD` 후 `git switch <기준-브랜치> && git merge --ff-only <브랜치>`.
6. 병합 후 백업 ref를 지운다: `git update-ref -d refs/backup/<브랜치>-pre-squash`
7. 작업 브랜치를 삭제한다: `git branch -d <브랜치>`

커밋 메시지는 한글, 컨벤셔널 커밋(`feat:`/`fix:`/`refactor:`/`style:`/`docs:`/`test:`/`chore:`
등)으로 쓰고, `claude`, `Generated with`, `Co-Authored-By`, `Claude-Session` 문구를 넣지 않는다.

## 마무리

checklist의 완료 조건을 전부 만족하면:

1. `pending-traps/`, `pending-issues/`를 훑어 승격 여부를 판단한다(아래 기준).
2. ROADMAP.md 항목에서 시작한 작업이면 `ROADMAP.md`에서 해당 항목을 완료로 표시한다.
   브레인스토밍에서 시작한 작업이면 이 단계는 없다.
3. "브랜치와 병합"에 따라 재그룹화 후 기준 브랜치에 병합한다.
4. `_meta.md`의 `상태`를 `완료`로 바꾼다.
5. 작업 폴더를 `_works/_completed/<원래 폴더명>/`으로 옮긴다(`mv`, 이름은 그대로 —
   이미 `yyyyMMdd-NN-<제목>` 형식이라 재명명하지 않는다). `_works/`가 통째로 gitignore
   대상이라 이 이동은 git에 기록되지 않는다.

`ROADMAP.md`·ADR·GitHub issue·소스 주석 같은 추적 대상에는 `_works/` 경로를 적지 않는다 — 다른
환경에서는 그 경로가 없다. 출처는 RD 번호·커밋 해시·ADR 링크로 남긴다.

### 함정 → 장기 문서화

모두 만족해야 승격: (1) 다시 겪을 조건을 특정할 수 있다 (2) 성공한 것처럼 보이는 신호가
있어 조용히 넘어갈 위험이 있다 (3) 재발 가능성이 있다.

승격하면 `docs/traps/`에 `INDEX.md` + `TRP-NNN-<slug>.md`(3자리, 001부터, 삭제한 ID 재사용
안 함) 형식으로 기록한다. 처음 승격할 때 디렉터리와 `INDEX.md`를 만든다. 승격 문서는 추적
문서이므로 `_works/` 경로와 DELTA 번호를 적지 않는다.

```markdown
# TRP-NNN <제목>

- 상태: ACTIVE
- 적용 조건: <무엇을 할 때 해당하는지>

## 오해하기 쉬운 신호

## 원인

## 탐지/회피
```

승격하지 않으면 그 작업 폴더의 `pending-traps/`에만 남고 자연 소멸한다.

### 후속 작업 → 등록

- 현재 ROADMAP.md 항목의 범위 안이면 그 항목의 하위 항목으로 `ROADMAP.md`에 삽입한다.
- 범위 밖이거나 ROADMAP.md와 무관한 작업(브레인스토밍 시작 포함)이면
  GitHub issue로 등록한다(`docs/agents/issue-tracker.md`).
- 등록 여부는 매번 판단한다 — 사소하면 버려도 된다.

## 금지

- `git rebase -i`, `GIT_SEQUENCE_EDITOR` 우회
- 재그룹화 없이 기준 브랜치에 병합(커밋이 그대로 늘어나는 것 방지)
- 기준 브랜치로 rebase 또는 push
- `git reset --hard`, force push, 광범위한 `git clean`
